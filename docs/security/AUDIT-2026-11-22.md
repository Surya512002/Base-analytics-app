# Security audit — 2026-11-22: can a user's wallet be drained?

Question asked: if an attacker finds a bug, can the wallets of people who trade in the app be
drained, through the limit orders or any other section?

Scope: every Solidity contract (LimitOrderBook, UniswapV3Adapter, BaseVoucher,
BaseVoucherCampaign, BaseDrops, TokenBalanceGate), the live order book's on-chain settings, and
every app path that asks a wallet to approve, send or sign: swaps, lending, limit orders,
vouchers, drops, sign-in, x402. Plus headers, uploads, user content and dependencies.
Method: line-by-line code review and read-only calls to Base mainnet. Nothing was signed or sent.

## Short answer

- **No contract lets an outsider take a user's funds.** No contract can pull tokens from a
  wallet except the wallet that is calling it. An approval given to the order book, voucher or
  drop contracts can't be spent by anyone else.
- **The real exposure is in the app**: two flows ask the wallet to approve a spender address
  that comes from an outside API or a server response, without checking it against a fixed
  list. A tampered quote or a compromised third-party API could make a user approve an attacker.
  These are fixable in the browser code (findings 1 and 2).
- No permit or Permit2 signatures are requested anywhere, which is the most common way wallets
  get drained by a signature alone.

## Findings

| # | Severity | Area | Finding |
|---|----------|------|---------|
| 1 | **High** | Swap | Approval spender and swap target come from the quote response unchecked |
| 2 | **High** | Lend & Stake | Vault addresses from third-party APIs become approval spenders, with an "unlimited" option |
| 3 | Medium | Headers | CSP allows `unsafe-inline` / `unsafe-eval`, so any future XSS could prompt wallet transactions |
| 4 | Medium | Server keys | Ticket signer keys can authorise claims; a leak lets someone drain ticket-gated drops |
| 5 | Medium | Order book | Not externally audited; some admin switches have no timelock |
| 6 | Low | BaseVoucher | Card secret travels in plain calldata at redeem (front-run window) |
| 7 | Low | BaseVoucher | Fee-on-transfer tokens are accepted, so such a batch can under-pay or eat into another batch of the same token |
| 8 | Low | x402 client | Unused helper that would sign any payment a 402 response asks for |
| 9 | Info | Dependencies | 41 advisories (24 high, 0 critical), all transitive in wallet/Coinbase SDKs |

### 1. Swap: spender and target taken from the quote (High)

`hooks/wallet/useAppTransactions.ts` approves `quote.allowanceSpender ?? quote.tx.to` (aggregator
route) or `quote.router` (direct routes), then sends calldata to `quote.tx.to` / `quote.router`.
All of these come from `/api/launchpad/quote`, which copies 0x's response as is
(`lib/launchpad/zerox.ts`). The only check is "the address has code" (`routerHasCode`, which
also passes when the RPC fails).

Impact: if the 0x API, our quote route or its hosting were compromised, or a bug returned a
wrong address, users would approve and send to an attacker contract. Approvals are exact (not
unlimited), so the loss is bounded by the trade amount, not the whole wallet.

Fix: one fixed allowlist in the browser (Uniswap SwapRouter02, Aerodrome Router, Slipstream
routers, 0x AllowanceHolder, the o1 router) and refuse anything else; also reject 0x quotes on
the server whose `transaction.to` or allowance spender is not the AllowanceHolder. Same pattern
as `assertAllowedLimitOrderTx` in `src/lib/limitOrders/calls.ts`, which already does this well.

### 2. Lending: discovered vault addresses become spenders (High)

Discovery adapters (`lib/lending/discovery/adapters/beefy.ts`, `pendle.ts`, `zkfi.ts`,
`aerodrome.ts`) read market addresses from outside APIs at runtime. `ActionDrawer` approves
`option.contractAddress` and, if the user ticks "unlimited", approves `maxUint256`.

Impact: if one of those APIs were compromised, users would approve an attacker contract. With
"unlimited" ticked, that approval covers the user's entire balance of that token, now and later,
until revoked.

Fix: allow transactions only to vault addresses on a reviewed list in the repo; show newly
discovered markets as read-only (link out) until added. Remove the unlimited option, or allow it
only for the fixed core protocols (Morpho Blue, Aave, Moonwell).

### 3. CSP allows inline and eval'd scripts (Medium)

Live header: `script-src 'self' 'unsafe-eval' 'unsafe-inline'`. No XSS was found: React escapes
text, React 19 blocks `javascript:` links, uploads are sniffed by their bytes and only served as
PNG/JPEG/WebP/GIF, remote SVG logos are rasterised. But if one ever appears, the CSP would not
stop it, and a script on our domain can ask the user's wallet to sign anything. Known since the
2026-11-17 audit (#12); a nonce-based CSP is the fix, at some hosting cost.

### 4. Server signing keys (Medium, operational)

`DROPS_TICKET_SIGNER_KEY` and `CAMPAIGN_CLAIM_SIGNER_KEY` sign claim tickets. On-chain rules
still apply (per-wallet limits, link proof for campaigns), but a leaked ticket key lets someone
claim ticket-gated drops from many wallets up to their budget. Drops are not on mainnet yet.
Keep these as Sensitive variables in Vercel only, use different keys per environment, and have
a rotation plan (`setTicketSigner` exists on BaseDrops).

### 5. Order book: unaudited, some instant admin switches (Medium)

The code is careful: fills must be within 1–3.5% of Chainlink, cancel always works (even when
paused), risky market changes wait 2 days. But it has had no external audit, and the owner Safe
can instantly turn off the keeper allowlist, change the adapter's pool fee tier, or raise the
keeper fee to at most 1%. The 2-of-3 Safe mitigates this. Keep the canary caps ($50 per order,
$500 per market) until an external audit.

### 6–7. BaseVoucher (Low)

The original gift-card contract sends the card secret in plain calldata when redeeming, so
someone who sees the pending transaction could copy it (hard on Base, which has no public
mempool). It also accepts fee-on-transfer tokens without checking the amount received, so such
a batch can come up short, at the expense of other batches of the same token. The newer
BaseVoucherCampaign and BaseDrops contracts fix both. Prefer them for new gifts.

### 8. Unused x402 client (Low)

`lib/x402-client.ts` is imported nowhere. If wired in as is, it would sign whatever USDC payment
any 402 response asks for, to any payee. Delete it, or add an amount cap and payee allowlist.

### 9. Dependencies (Info)

`npm audit --omit=dev`: 41 advisories, 24 high, 0 critical. All are transitive through
`@coinbase/onchainkit`, `@coinbase/cdp-sdk`, `@base-org/account`, Reown/WalletConnect and
Farcaster SDKs (hono, fast-uri, ws, body-parser, decode-uri-component). They are server or
DoS-type issues in libraries we don't run as our server, not browser wallet-drain paths.
Upgrade in a separate PR.

## Checked and OK

- **LimitOrderBook** only pulls from `msg.sender`; every fill is checked against Chainlink with a
  per-market bound; stale feeds and a down sequencer block execution; reentrancy guard on every
  state change; fee-on-transfer rejected; brackets refund once; escrow accounting can't block exits.
- **UniswapV3Adapter**: only the order book can call `swap`; it holds no funds.
- **Live order book (read on 2026-11-22)**: owner and adapter owner are the 2-of-3 Safe, guardian
  set, `keeperOnly` on, sequencer feed set, keeper fee 0.10%, $500 quote escrow cap on every
  market, no pending risk change, every market on the expected adapter.
- **Limit-order transactions in the app**: target and spender allowlisted, exact approvals, no ETH.
- **BaseVoucherCampaign / BaseDrops**: wallet-bound signatures, malleable signatures rejected,
  one-time codes, refunds only to the creator, fee-on-transfer rejected, reentrancy guards.
  TokenBalanceGate keys rules by the calling contract, so nobody can overwrite another drop's rule.
- **Voucher card secrets**: 20 characters from a secure random source (about 100 bits); can't be
  guessed from the on-chain hashes.
- **Signatures**: only plain-text sign-in messages; no permits.
- **Uploads, logos, placeholder SVGs**: no script can be served from our domain.

## Fixed in the same PR

- **1 and 2:** every wallet transaction now goes through `assertTrustedApprovals`
  (`lib/security/trusted-spenders.ts`, called in `sendAppTransactions`). An approval to any
  contract not on the list is refused before the wallet is asked, and "approve all NFTs" is
  always refused. Unlimited approval is allowed only for Morpho, Aave and the fixed core markets.
  Swaps also check that the call target is a known router (`isTrustedSwapTarget`), and the server
  drops 0x quotes that don't point at the AllowanceHolder. Discovered lending markets outside
  `lib/security/reviewed-lending-contracts.json` (75 contracts, each checked to hold code on Base
  on 2026-11-22) are shown but can't be deposited into.
- **8:** `lib/x402-client.ts` deleted.
